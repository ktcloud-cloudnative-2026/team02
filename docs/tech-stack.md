## 선정 상태

**전체 상태: 기술 스택 초안 · 최종 승인 필요.** 기획서 8장에 기술명이 있으나 요구사항과 결정 기록은 최종 기술 스택을 미결정으로 기록합니다. 기술명이 반복되어도 승인을 추정하지 않습니다. [PD-04](pending-decisions.md#pd-04) 참고.

기존 GitHub 기술 스택 표는 선택·이유·대안이 비어 있는 템플릿이었습니다. 아래 표에는 Notion에 실제 언급된 기술과 이유만 정리했습니다. 버전, 메시지 큐·로그 제품, 버린 대안은 만들지 않았습니다.

| 영역 | 원문에 기재된 기술·방식 | 선정 상태 | 원문에서 제시한 역할·이유 |
|---|---|---|---|
| 프론트엔드 | React, Nginx | 제안 · 최종 승인 필요 | 프론트엔드 구성으로 기재. 개별 선정 이유는 미기재 |
| 백엔드 | Spring Boot | 제안 · 최종 승인 필요 | Spring 트랜잭션을 통한 재고 정확성, 학습한 조합 활용 |
| 인증·인가 | Spring Security·OAuth2 | 명시적 제안 · 기능 범위 승인 필요 | 고객·관리자 권한 구분, 로그인·소셜 로그인. 확정 기술이 아님 |
| 데이터베이스 | PostgreSQL, 서비스별 DB 분리 | 제안 · 최종 승인 필요 | 행 잠금으로 재고 정확성 유지. 물리 배치·접근 권한은 미결정 |
| 게이트웨이 | Envoy Gateway | 제안 · 최종 승인 필요 | 게이트웨이 구성·실습 대상으로 기재. 세부 라우팅 미작성 |
| 배포 환경 | Kubernetes(kubeadm) | 제안 · 최종 승인 필요 | 독립 배포·배포 자동화와 장애 복구 검증 |
| CI/CD | GitHub Actions + GitOps | 제안 · 최종 승인 필요 | 배포 자동화. GitOps 구현 도구의 최종 선택은 확인 필요 |
| 메트릭·대시보드 | Actuator·Micrometer·Prometheus·Grafana | 제안 · 최종 승인 필요 | 메트릭 수집과 관측. 자체 모니터링 화면은 Prometheus 지표 활용안 |
| 중앙 로그 | 중앙 로그 수집 | 제품 미결정 | 주문 흐름 추적과 장애 관측. 원문은 구체 제품을 선정하지 않음 |
| 서비스 간 통신 | 동기·비동기 혼합, 주문·조리 이벤트 요구안 | 적용 방식·제품 미결정 | SR-06의 이벤트 요구와 상세 설계 미결정을 함께 검토 |
| 소셜 로그인 | 외부 제공자(예: Google·Kakao) | 후보 예시 · 범위·제공자 미결정 | 기획서에 개발자 앱 등록 필요로 기재. 둘 중 하나를 선택한 것이 아님 |
| AI·ML 항목 | Claude, ChatGPT | 원문 기재 · 구체 용도·선정 상태 확인 필요 | 기획서 AI·ML 항목에 기재. 사용자 대상 AI 기능이나 런타임 의존성을 추가하지 않음 |

## 원문에 기재된 사용 이유

- 핵심은 동시 주문 정확성과 업무 지연·시스템 장애의 구분입니다.
- 학습한 조합을 활용해 배포 자동화·관측에 시간을 집중한다는 이유가 기획서에 있습니다.
- Spring 트랜잭션·PostgreSQL 행 잠금, Spring Security 권한 구분, Kubernetes·관측 도구의 역할은 기획서의 설명이며 검증 완료 결과가 아닙니다.
- 인증·관리자 범위와 서비스 수 자체가 충돌하므로 기술 적용 대상도 최종 승인 전입니다.

## 추가 검토가 필요한 항목

- 기술별 버전·런타임·의존성 목록과 최종 승인 근거: 미제공.
- 운영 DB의 실제 배치와 서비스별 DB·권한 구분: 미결정.
- 메시지 큐 도입 여부·제품, 동기·비동기 적용 지점, 재시도·복구 방식: 미결정.
- 중앙 로그 제품, 최종 GitOps 도구, 인증·소셜 로그인 상세: 확인 필요.
- Istio·카나리 배포·자동 롤백은 기획서 COULD 항목이며 기본 스택으로 채택하지 않습니다.
- 기존 배포 README의 Argo CD 등은 이번에 변경하거나 새로 승인한 항목이 아닙니다. [PD-15](pending-decisions.md#pd-15) 참고.

## 고르는 기준

기존 문서의 검토 기준을 유지합니다.

- [비기능 요구사항](requirements.md)의 목표를 만족하는가?
- 팀이 운영할 수 있고 학습·구현 시간이 충분한가?
- 제공된 클러스터 자원에서 운영 가능한가?
- 대안과 비교했는가? 원문에 없는 버린 대안과 이유는 작성하지 않습니다.

선정이 승인되면 근거를 [설계 결정 기록](adr/0001-template.md)으로 남기고 이 문서의 상태를 맞추는 방식으로 후속 정리할 수 있습니다. 이번 단계에서는 ADR이나 의존성 파일을 만들지 않습니다.
