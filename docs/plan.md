## 1. Problem — 해결하려는 문제

> 음식점의 피크 시간대에 주문이 집중되면서 자신의 주문 진행 상황이나 예상 대기 시간 파악이 어려워짐. 또한 여러 유저가 제한된 재고를 동시에 주문하거나 시스템 장애가 발생하면 주문 처리의 정확성과 서비스 이용이 영향을 받을 수 있음.
>
- 작성 기준
    - 프로그램이나 기술을 설명하지 않는다. 현재 상태의 문제만 쓴다
    - 나쁜 예: "AI를 활용한 분리수거 시스템이 필요하다" → 이건 해결책이지 문제가 아니다
    - 좋은 예: "자취생은 품목별 분리배출 기준을 몰라 ○○한 상황에서 잘못 배출하고, 그 결과 ○○가 발생한다"

## 2. Target User — 목표 사용자

- **핵심 사용자** : 점심·저녁 피크 시간대에 매장 앱으로 주문하고 매장에서 대기하는 고객 (비회원 X, 오로지 회원만 사용가능)
- **보조 사용자** : 매장 운영자. 매장 관리자는 재고·혼잡도를 관리하고, 장애 대응 관리자는 장애 시 주문 접수를 중지·재개함
- **사용 상황** :  주문이 몰려 대기 인원이 많을 때, 주문 후 본인의 주문번호를 보며 조리 완료를 확인하고, 전광판을 보며 예상 대기 시간을 확인해야하는 상황 + 운영자는 피크 시간에 혼잡 상태를 확인하고, 장애가 나면 원인을 보고 주문 접수를 멈춰야 하는 상황
- **접근 · 검증 방법** : 피크 시간 주문 흐름을 확인, 팀원·수강생 대상 시연 후 의견 수집, 팀원이 운영자 역할을 맡아 장애 대응 시연
- 작성 기준

    "대학생", "일반 사용자"처럼 넓게 쓰면 감점 요인이다. 사용 상황까지 포함해 좁힌다.

    실제로 만나거나 설문할 수 있는 사용자인지도 함께 확인한다.


## 3. Cause · Context — 원인 및 상황

> [가설]  피크 시간에는 주문이 하나의 조리 대기열에 몰리는데, 고객에게 대기열 상태가 보이지않는다.
>

> [가설] 여러 명이 마지막 재고를 동시에 결제하면 실제 재고보다 많이 팔리는 초과 판매가 생길 수 있다.
>

> [가설] 하나의 서버로는 모든 기능을 처리하게 되면 한 기능의 장애가 주문 전체를 멈추게 한다.
>

> [가설] 운영 측에서는 “주문이 많아서 느린 상황” 과 “시스템 고장으로 느린 상황” 을 구분하기 어렵다.
>

> [가설] 운영자에게 혼잡 정도를 보여 주는 지표와 장애 시 주문을 멈출 수단이 없어, 대응이 늦어지고 실패한 주문이 쌓인다.
>

> **상태: 제안 · 승인 필요.** 아래는 기획서 원문에 적힌 6개 서비스 안입니다. 3개·5개 안과 충돌하며, 장바구니 시점 재고 확보는 같은 문서의 MUST 2번 및 US-03·04와도 다릅니다. 최종 구성이나 재고 정책으로 확정하지 않습니다. [PD-01·03](pending-decisions.md) 참고.

## 4. Proposed Solution — 제안 해결방법

> 피크오더는 **메뉴·주문·조리·혼잡도·인증·관리자** 6개의 독립 서비스로 나눈다. 메뉴를 장바구니에 담은 시점부터 재고를 확보해 동시에 주문이 몰려도 정확하게 처리하고, 회원가입·로그인으로 고객과 관리자의 권한을 구분한다. 고객은 공용 전광판에서 주문 상태와 예상 대기 시간을 확인하고, 혼잡도 서비스는 주문량과 대기열을 분석해 매장의 혼잡 상태를 산정한다. 관리자는 대시보드에서 각 매장의 재고와 혼잡도를 관리한다. Kubernetes 배포 자동화와 모니터링으로 업무상 지연과 시스템 장애를 구분하고, 장애 시 신규 주문을 제한한다.
>

> **상태: 승인 필요.** MUST·SHOULD·COULD·WON’T는 원문이 제시한 우선순위이며, 팀 승인을 뜻하지 않습니다. 로그인·관리자 기능은 요구사항·결정 기록과 충돌합니다. [PD-02](pending-decisions.md#pd-02) 참고.

## 5. Core Functions — 프로젝트 범위

### MUST — 반드시 구현

1. 메뉴 조회 → 장바구니 → 모의 결제 → 주문번호 발급
2. 결제 시 재고 임시확보(1분), 성공 시 확정 차감, 실패·취소·만료 시 반환 (초과 판매 방지)
3. 공용 FIFO(선입선출) 대기열과 공용 전광판 (주문번호·진행 상태·예상 대기 시간)
4. 조리 시작 전 주문 취소와 재고 복원
5. 화면별 로그인과 권한 구분 (Auth)
    - 사용자 화면: 고객 회원가입·로그인, 소셜 로그인, 비밀번호 찾기
    - 운영자 대시보드: 관리자 로그인 (회원가입 없음, 최고 관리자가 계정 생성)
    - 권한 : 고객 / 최고 관리자 / 장애 대응 관리자 / 매장 관리자
6. 주문량·대기열 기반 혼잡도 자동 산정과 혼잡 상태 제공 (Congestion)
7. 운영자 대시보드 (Admin) — 사용자 화면과 별도 사이트, 권한별 메뉴
    - 최고 관리자: 관리자 계정 생성, 권한 부여·회수
    - 장애 대응 관리자: 자체 개발한 모니터링 화면 + 신규 주문 접수 중지·재개 스위치 (수동)
    - 매장 관리자: 재고 등록·수정, 혼잡도 확인과 기준값 설정
8. Kubernetes 배포 + PR 기반 자동 배포(CI/CD) — 6개 서비스 모두
9. 서비스별 메트릭·로그 수집과 대시보드

### SHOULD — 가능하면 구현

1. 조리 서비스 장애 자동 감지 시 신규 주문 제한
2. 업무 지연(조리 대기)과 시스템(API·DB)을 구분하는 대시보드와 장애 알림
3. S1~S4 시나리오 스크립트 (정상 주문, 주문 집중, 시스템 장애, 집중 중 장애)
4. 관리자 작업 기록 (누가 언제 어떤 조치를 했는지)

### COULD — 시간이 충분하면

1. 운영용 챗봇 (디스코드에서 지연 원인 요약)
2. 카나리 배포와 자동롤백
3. 서비스 메시(Istio)로 장애 격리
4. 장애 대응 관리자 페이지에서 서비스 일시 중단 (Kubernetes 직접 조작)
5. 다중 매장 : 매장 선택, 매장별 재고·대기열·전광판·혼잡도, 매장 관리자의 담당 매장 구분

### WON'T — 이번 프로젝트에선 X

1. 주문번호 검색 화면
2. 실제 결제, 배달
3. 여러 조리 생산라인, 동시 다건 조리, 복잡한 조리 스케줄링

⚠️

WON'T를 비워두지 않는다. 무엇을 하지 않을지 정하는 것이 범위 관리의 핵심이고, 심사에서도 실현 가능성 판단의 근거가 된다.

> **상태: 제안.** 아래는 성공 목표이며 달성 결과가 아닙니다. 100명 동시 결제 등 수치는 승인된 테스트 조건으로 간주하지 않고, `[N]초`는 원문의 미정 값으로 유지합니다. [PD-08](pending-decisions.md#pd-08) 참고.

## 6. Success Metrics — 성공지표

- **무엇을 측정**: 재고 정확성, 주문 상태 안내, 장애 감지·대응, 권한별 접근 제어, 혼잡도 산정
- **어떻게 측정**: 동시 주문 테스트, 장애 재현 시나리오, 권한별 접근 테스트
- **평가 대상**: 피크오더 전체 서비스 (**dev** 환경)
- **성공 판단 기준** :
    1. 마지막 재고 1개에 100명 동시 결제 → 1명만 성공, 음수 재고 0건
    2. 결제하지 않고 1분 지나면 재고 자동 반환
    3. 주문 집중(요청 증가, 에러 0)과 시스템 장애(에러·응답 시간 증가)를 대시보드에서 구분 가능
    4. 조리 서비스 장애 시 장애 대응 관리자가 신규 주문 접수를 중지하면 신규 주문이 거절되고, 복구 후 재개하면 정상 접수
    5. PR 병합 후 dev 환경에 자동 배포
    6. 권한 밖 접근 차단 100% : 고객 계정의 운영자 대시보드 접근, 매장 관리자의 계정 관리 메뉴 접근 등이 모두 거절됨
    7. 대기열이 매장 관리자가 정한 기준값을 넘으면 혼잡 상태로 바뀌어 표시됨
    8. 장애를 주입하면 자체 모니터링 화면에 [N]초 안에 장애 상태가 표시됨
- 작성 기준

    "사용자가 편리할 것이다" 같은 표현만으로는 안 된다. 관찰하거나 측정할 수 있는 형태로 쓴다.

    예: 분류 정확도 85% 이상 · 탐색시간 30% 감소 · 5점 만점 만족도 4.0 이상 · 응답 지연 2초 이하


> **상태: 미결정·제안 포함.** 개발 기간과 역할 재분담은 확정되지 않았습니다. 담당자를 임의로 배정하지 않습니다. DB 배치는 다른 원문과 함께 검토해야 합니다. [PD-06·09·10](pending-decisions.md) 참고.

| 구분 | 우리 프로젝트에서 고려할 사항 |
| --- | --- |
| 시간 | [미정] 발표·보고서 기간 제외 실제 개발 기간 확인 필요 |
| 인원 및 역할 | 6명, 서비스 6개 + 화면 2종(사용자·운영자). 기능 분할 재조정 필요 (제안: 프론트 / 메뉴+게이트웨이 / 주문 / 조리+혼잡도 / 인증+관리자 / 인프라·관측), 클라우드 공통 영역을 하나씩 배정 |

| 데이터 | 실제 고객 데이터 없음, 메뉴 시드 데이터와 테스트용 가짜 주문, **테스트 계정(고객·관리자 3종)**으로 검증 |
| 비용 · 장비 | 강사 제공 개발·배포 환경, 팀 공용 PostgreSQL VM 사용, 소셜 로그인은 외부 제공자(예: Google·Kakao) 개발자 앱 등록 필요 |
| 개인정보 · 윤리 · 저작권 | 회원가입 시 최소 정보만 수집(예: 이메일), 비밀번호는 해시로 저장, 전광판에 개인정보·상세 주문 미노출, 소셜 로그인 키를 포함한 시크릿은 Kubernetes Secret으로 관리 |

> **상태: 기술 스택 초안 · 최종 승인 필요.** React·Spring Boot·PostgreSQL을 포함한 아래 기술은 확정 목록이 아닙니다. 원문에 적힌 사용 이유를 보존하며, 선정 상태는 [기술 스택](tech-stack.md)에 정리합니다.

## 8. Technology — 활용 기술

- **Front-end** : React, Nginx
- **Back-end** : Spring Boot (메뉴·주문·조리·혼잡도·인증·관리자 6개 서비스), Spring Security·OAuth2 (로그인·소셜 로그인·권한, 제안)
- **AI · ML** : Claude , ChatGpt
- **Database · API · 기타** : PostgreSQL(서비스별 DB 분리), Envoy Gateway, Kubernetes(kubeadm), GitHub Actions + GitOps, Actuator·Micrometer·Prometheus·Grafana, 중앙 로그

**이 기술을 쓰는 이유**

- 프로젝트에서 수행하는 역할 : Spring 트랜잭션과 PostgreSQL 행 잠금으로 재고 정확성을 지키고, Spring Security로 고객·관리자 권한을 나누며, Kubernetes와 관측 도구로 배포·장애 대응을 자동화한다. 자체 모니터링 화면은 Prometheus에 모인 지표를 가져와 보여 준다
- 반드시 필요한 이유 : 피크오더의 핵심은 동시 주문 정확성과 장애 구분이며, 국비과정에서 학습한 조합을 써서 새 기술 학습 대신 P2 핵심(배포 자동화·관측)에 시간을 집중한다

## 10. 한 문장 정의

> 주문 앱의 점주용 관리 화면우리 팀은 **음식점 고객과 매장 운영자**가 **피크 시간대 주문이 몰리는** 상황에서 겪는 **주문 진행·대기 시간을 알 수 없고, 재고·장애로 주문이 잘못 처리되며, 운영자가 혼잡과 장애를 구분해 대응하기 어려운** 문제를 해결하기 위해 **피크오더(MSA 기반 주문·조리 대기 및 운영 관리 서비스)**를 개발하고, 그 효과를 **재고 경쟁·장애 시나리오 테스트와 모니터링 지표**로 평가한다.
