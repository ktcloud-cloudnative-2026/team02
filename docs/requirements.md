## 1. 기능 요구사항

### US-01 메뉴 목록 조회

- 사용자는 메뉴 목록에서 메뉴명, 가격, 품절 여부를 볼 수 있다
- 수용 기준
    - [ ]  목록에 메뉴명·가격·품절 여부가 표시된다
    - [ ]  재고가 0인 메뉴는 품절로 표시되고 선택할 수 없다
    - [ ]  메뉴·옵션·초기 재고·기본 조리 시간은 사전 설정된 시드 데이터에서 온다
- 담당 서비스: 메뉴(4번) · 화면: 프론트(1번)

### US-02 메뉴 상세·옵션·수량 선택

- 사용자는 메뉴 상세에서 옵션과 수량을 선택할 수 있다
- 수용 기준
    - [ ]  메뉴별 옵션이 표시되고 선택한 옵션에 따라 가격이 반영된다
    - [ ]  수량은 1 이상이어야 하고, 재고를 넘는 수량은 선택할 수 없다
- 담당 서비스: 메뉴(4번) · 화면: 프론트(1번)

### US-03 장바구니

- 사용자는 여러 메뉴를 장바구니에 담고, 수량 변경·항목 삭제·주문 금액 확인을 할 수 있다
- 수용 기준
    - [ ]  서로 다른 메뉴 여러 개를 담을 수 있다
    - [ ]  수량 변경과 항목 삭제가 즉시 반영되고 합계 금액이 갱신된다
    - [ ]  장바구니에 담는 것만으로는 재고가 변하지 않는다
- 담당 서비스: 프론트(1번)

> **원문상 결정 · 팀 전체 최종 승인 확인 필요.** Notion [설계 결정 기록](https://puzzling-woolen-3e9.notion.site/40f2f07e947880e79b0bd511e54367a5?source=copy_link)의 ‘후속 작업’에는 “장바구니 저장 위치 : 프론트엔드 관리로 결정됨”이라고 적혀 있습니다. 원문 결정을 보완 기록한 것이며 팀 전체의 최종 승인이 확인된 것은 아닙니다. 구체적인 저장 기술은 정하지 않습니다.

### US-04 모의 결제 시도와 재고 임시 확보

- 사용자는 장바구니 내용으로 모의 결제를 시도할 수 있고, 이때 전체 재고가 임시 확보된다
- 수용 기준
    - [ ]  결제 버튼을 누르는 시점에 장바구니의 모든 품목 재고가 한꺼번에 임시 확보된다
    - [ ]  임시 확보는 1분간 유효하고 화면에 남은 시간이 표시된다
    - [ ]  일부 품목이라도 재고가 부족하면 전체 확보에 실패하고 부족 안내가 표시된다(부분 확보 없음)
    - [ ]  실제 결제는 하지 않는 모의 결제이다
- 담당 서비스: 주문(2번) · 화면: 프론트(1번)

### US-05 주문 확정과 주문번호 발급

- 사용자는 결제에 성공하면 주문이 확정되고 주문번호를 받는다
- 수용 기준
    - [ ]  결제 성공 시 임시 확보 재고가 확정 차감된다
    - [ ]  주문번호가 발급되어 주문 완료 화면에 표시된다
    - [ ]  확정된 주문은 조리 대기열에 등록된다
- 담당 서비스: 주문(2번) → 조리(3번) 이벤트

### US-06 결제 실패·취소·만료 시 재고 반환

- 결제가 실패하거나 취소되거나 1분이 지나면 임시 확보 재고가 자동으로 반환된다
- 수용 기준
    - [ ]  결제 실패·사용자 취소·1분 만료 각각에서 재고가 원래 수량으로 복원된다
    - [ ]  만료된 건으로는 결제를 완료할 수 없고 결과가 안내된다
    - [ ]  반환 처리가 중복 실행되어도 재고가 초과 복원되지 않는다
- 담당 서비스: 주문(2번)

### US-07 중복 결제 방지

- 같은 주문에 대한 결제 요청이 여러 번 와도 한 번만 처리된다
- 수용 기준
    - [ ]  결제 버튼 연타·재시도 시 주문이 하나만 확정된다
    - [ ]  중복 요청에는 이미 처리된 결과가 반환된다
- 담당 서비스: 주문(2번)

### US-08 동시 주문 재고 경쟁

- 여러 사용자가 동시에 마지막 재고를 주문해도 초과 판매가 발생하지 않는다
- 수용 기준
    - [ ]  재고 1개를 N명이 동시에 결제 시도하면 정확히 1명만 확보에 성공한다
    - [ ]  재고가 음수가 되는 경우가 없다(DB 제약 조건으로도 차단)
    - [ ]  실패한 사용자에게는 재고 부족이 안내된다
- 담당 서비스: 주문(2번)

### US-09 공용 FIFO 대기열과 자동 조리

- 확정된 주문은 들어온 순서대로 대기열에 쌓이고, 한 번에 1건씩 자동으로 조리된다
- 수용 기준
    - [ ]  주문 확정 순서(FIFO)대로 조리가 시작된다
    - [ ]  동시에 조리 중인 주문은 최대 1건이다(서버를 여러 개 띄워도 동일)
    - [ ]  메뉴별 기본 조리 시간이 지나면 자동으로 완료 처리된다
    - [ ]  조리 시작·완료가 주문 서비스에 이벤트로 전달된다
    - [ ]  조리 서비스가 재시작되어도 대기열 상태가 유지된다
- 담당 서비스: 조리(3번)

### US-10 예상 대기 시간

- 사용자는 내 주문의 예상 대기 시간을 볼 수 있다
- 수용 기준
    - [ ]  앞선 대기 주문의 조리 시간 합으로 예상 대기 시간이 계산된다
    - [ ]  앞선 주문이 완료되거나 취소되면 예상 시간이 갱신된다
- 담당 서비스: 조리(3번) · 화면: 프론트(1번)

### US-11 조리 시작 전 주문 취소

- 사용자는 조리가 시작되기 전에 본인 주문을 취소할 수 있다
- 수용 기준
    - [ ]  조리 대기 상태에서 취소하면 주문이 취소되고 재고가 복원된다
    - [ ]  취소 가능 여부는 조리 서비스가 판단한다
    - [ ]  조리가 시작된 주문은 취소할 수 없고 그 사유가 안내된다
    - [ ]  부분 취소는 지원하지 않는다(주문 전체 취소만)
- 담당 서비스: 주문(2번) + 조리(3번) · 화면: 프론트(1번)

### US-12 공용 주문 전광판

- 누구나 공용 전광판에서 주문번호, 현재 상태, 예상 대기 시간을 볼 수 있다
- 수용 기준
    - [ ]  주문번호·상태·예상 대기 시간만 표시한다
    - [ ]  개인정보와 상세 주문 내역은 노출하지 않는다
    - [ ]  새로고침 없이 상태가 갱신된다
    - [ ]  주문번호 직접 검색 화면은 제공하지 않는다
- 담당 서비스: 주문(2번)·조리(3번)가 데이터 제공 · 화면: 프론트(1번)
- 미결정: 전광판 조회 API를 주문 서비스 안에 둘지 별도 읽기 서비스로 둘지는 팀 합의 필요(기능 6분할 문서 6장 참고)

### US-13 조리 서비스 장애 시 신규 주문 제한

- 조리 서비스에 장애가 있으면 신규 주문을 제한한다
- 수용 기준
    - [ ]  조리 서비스가 응답하지 않으면 메뉴 서비스에서 현재 이용불가하다고 표시된다
    - [ ]  이미 확정된 주문 데이터는 유지된다
    - [ ]  조리 서비스가 복구되면 신규 주문이 다시 허용된다
- 담당 서비스: 주문(2번)

> **SR-01~06 상태: 승인 필요.** 배포·관측·게이트웨이·비동기 통신의 요구안입니다. SR-06의 이벤트 전달 요구와 아키텍처·결정 기록의 통신 적용 미결정은 함께 검토해야 합니다. 메시지 큐 제품을 선택한 것으로 간주하지 않습니다. [PD-05](pending-decisions.md#pd-05) 참고.

## 2. 시스템 요구사항 (P2 과제 · 배포 자동화, 모니터링, 로깅)

### SR-01 Kubernetes 배포 자동화

- 공식 저장소 변경 사항이 Kubernetes 개발 환경에 자동 배포된다
- 수용 기준
    - [ ]  PR 병합(main) 시 이미지 빌드 → dev 배포가 자동으로 이어진다
    - [ ]  배포 실패 시 이전 버전으로 되돌릴 수 있다
    - [ ]  dev와 prod는 별도 클러스터이며 환경별 설정이 분리된다
- 담당: 클러스터·GitOps(5번), CI 파이프라인(1번)

### SR-02 모니터링(메트릭)

- 서비스별 상태를 메트릭으로 확인할 수 있다
- 수용 기준
    - [ ]  서비스마다 요청 수·오류율·응답 시간 대시보드가 있다
    - [ ]  업무 지연(조리 대기열 길이·대기 시간)과 시스템 지연(API·DB·인프라)을 분리해서 볼 수 있다
    - [ ]  오류율·재시작·지연이 임계치를 넘으면 알림이 발생한다
- 담당: 관측·신뢰성(6번), 각 서비스 오너는 자기 서비스의 메트릭 출력

### SR-03 중앙 로깅

- 모든 서비스의 로그를 한곳에서 검색할 수 있다
- 수용 기준
    - [ ]  로그에 traceId, orderId 같은 공통 필드가 있다
    - [ ]  주문번호 하나로 주문·조리 서비스의 흐름을 이어서 추적할 수 있다
    - [ ]  파드가 재시작되어도 이전 로그가 남아 있다
- 담당: 관측·신뢰성(6번), 각 서비스 오너는 공통 필드가 들어간 로그 출력

### SR-04 장애 감지와 자동 복구

- 장애를 감지·기록하고 자동으로 복구된다
- 수용 기준
    - [ ]  liveness·readiness 점검이 설정되어 비정상 파드가 자동 재시작된다
    - [ ]  복구 후 주문·재고 데이터가 유지된다
    - [ ]  장애 발생과 복구 과정이 메트릭과 로그로 설명 가능하다
- 담당: 각 서비스 오너(헬스 체크·graceful shutdown), 관측·신뢰성(6번, 장애 시험), 클러스터(5번, 자동 재시작 환경)

> **기술적 보충 설명 · 팀 검토용(원문 외 주석).** 위 원본 수용 기준은 그대로 보존합니다. liveness 점검이 설정된 실패 기준에 도달하면 kubelet이 해당 컨테이너를 재시작합니다. readiness 점검 실패는 해당 파드를 Service의 트래픽 전달 대상에서 제외하며, 그 자체로 컨테이너를 재시작하지 않습니다. 최종 수용 기준은 이 역할 차이를 반영해 팀이 검토해야 합니다.

### SR-05 게이트웨이와 접근 제어

- 외부 요청은 게이트웨이를 통해서만 서비스에 도달하고, 서비스 간 접근은 허용된 경로로 제한된다
- 수용 기준
    - [ ]  프론트, 메뉴·주문·조리 서비스 경로가 게이트웨이에서 라우팅된다
    - [ ]  TLS가 적용되고 CORS·요청 제한이 설정된다
    - [ ]  비밀값은 Secret으로 관리되며 코드·저장소에 노출되지 않는다
    - [ ]  NetworkPolicy로 서비스 간 허용 경로만 열려 있다
- 담당: 메뉴 서비스 + 게이트웨이·보안(4번)

### SR-06 서비스 간 비동기 통신

- 주문 서비스와 조리 서비스는 이벤트로 상태를 주고받는다
- 수용 기준
    - [ ]  "주문 확정됨", "조리 시작됨", "조리 완료됨" 이벤트가 전달된다
    - [ ]  전달 실패 시 재시도되고, 계속 실패한 메시지는 별도 보관된다
    - [ ]  같은 이벤트가 중복 전달되어도 주문 상태가 한 번만 바뀐다
- 담당: 조리 서비스 + 메시징(3번), 이벤트 수신 처리는 주문(2번)

## 3. 시연·검증 시나리오

| ID | 시나리오 | 확인 사항 |
| --- | --- | --- |
| S1 | 정상 주문 | 메뉴 선택 → 결제 → 주문번호 → 대기 → 조리 완료 → 전광판 표시까지 정상 |
| S2 | 주문 집중 | 동시 결제에서 재고 정합성 유지, 대기열 증가, API·DB 부하와 업무 지연 구분 |
| S3 | 시스템 장애 | 오류·장애 감지와 기록, 복구 후 주문 데이터 유지, 상태 확인 |
| S4 | 주문 집중 중 장애 | 부하와 장애가 겹쳐도 오류·복구·재고·주문 정합성 유지 |

재고 경쟁(US-08)과 주문 취소(US-11)는 위 시나리오 안에서 함께 검증한다.

수행 담당: 관측·신뢰성(6번)이 주도하고, 각 서비스 오너가 자기 서비스 부분을 지원한다. 부하 스크립트와 장애 주입 방식은 B-5 설계에서 확정한다.

> **상태: 제안.** 원문이 이 절 전체를 제안값으로 표시했습니다. p95는 요청 중 95%가 해당 시간 이내에 응답하는지를 보는 지표입니다. 수치와 부하 조건은 팀 승인 전까지 목표안입니다.

> **기획서 참조 보충.** 위 “기획서(7장)”은 원문 표현입니다. 현재 GitHub 기획서의 성공 목표는 [6장 성공지표](plan.md#6-success-metrics--성공지표), 제약조건은 [7장 제약조건](plan.md#7-constraints--제약조건)을 참고합니다. 제안된 목표와 조건을 승인된 기준으로 간주하지 않습니다.

> **상태: 미결정 — 문서 충돌.** 아래는 요구사항 원문의 제외 목록을 보존한 것입니다. 로그인·관리자 제외는 기획서 MUST 및 아래 US-14~19와 충돌합니다. 기획서에서는 다중 매장이 COULD인 점도 함께 확인해야 합니다. 최종 제외 범위로 확정하지 않습니다. [PD-02·11](pending-decisions.md) 참고.

## 5. 범위 밖 (기획서 5.2)

> **기획서 참조 보충.** 제목의 “기획서 5.2”는 원문 표현입니다. 현재 GitHub 기획서에는 해당 번호의 절이 없으므로 [5장 프로젝트 범위](plan.md#5-core-functions--프로젝트-범위)의 MUST·SHOULD·COULD·WON’T 구분과 대조합니다. 두 문서의 범위 차이는 그대로 검토 대상으로 둡니다.

- 회원가입·로그인, 관리자 화면
- 실제 결제, 환불·배달·다중 매장
- 주문번호 직접 검색 화면
- 원재료 단위 상세 재고, 부분 주문 취소
- 여러 조리 생산라인, 동시 다건 조리, 복잡한 조리 스케줄링
- 생산라인 고장 등 별도 업무 시뮬레이션 기능

## 7. 팀원 승인 필요

### US-14 회원 가입 — 팀원 승인 필요
- 사용자는 회원가입 할 수 있다.
- 수용 기준
    - [ ]  아이디, 비밀번호 등 필수 정보를 입력해 가입
    - [ ]  아이디 중복 불가
    - [ ]  비밀번호는 암호화로 저장
- 담당: 미정

> **표현 차이 · 팀 확인 필요.** 위 “비밀번호는 암호화로 저장”은 Notion 요구사항 원문이며, [기획서의 개인정보·윤리·저작권 항목](plan.md#7-constraints--제약조건)은 “비밀번호는 해시로 저장”으로 적혀 있습니다. 암호화와 해시는 다른 방식입니다. 향후 비밀번호 저장 정책은 **안전한 단방향 해시 방식으로 검토할 사항**이며, 특정 제품·알고리즘·인증 방식을 확정하지 않습니다. [PD-17](pending-decisions.md#pd-17)에서 팀 확인 사항으로 관리합니다.

    - [ ]  정보 불일치 시 로그인 불가
