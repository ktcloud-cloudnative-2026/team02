## 상태와 검토 원칙

- **확정**: 팀 승인 근거가 확인된 항목. 현재 제공 자료만으로 최종 확정한 항목은 없습니다.
- **제안**: 원문에 적힌 후보·목표·설계안입니다.
- **미결정**: 원문에서 미정이거나, 문서 충돌로 최종 선택을 알 수 없습니다.
- **승인 필요**: 팀 검토·합의가 필요합니다. ‘원문에 결정이라고 적힘’과 ‘팀 전체 승인 확인’을 구분합니다.

아래 ID는 이번 문서 정리를 위한 쟁점 번호이며 새로운 기능이나 설계 결정이 아닙니다. 어떤 원문이 더 최신인지 추정하지 않았습니다. 담당자·기한·승인일은 자료로 확인되지 않아 배정하지 않습니다. 각 항목의 ‘확인 질문’은 검토를 위한 질문이며 요구사항을 추가하지 않습니다.

## PD-01

**백엔드 서비스 수와 책임 — 구성안 정리 완료 · 팀 최종 승인 대기**

### 현재 구성안

- **백엔드 5개 서비스:**
  - **Menu Service:** 메뉴·옵션·가격 정보 관리
  - **Order Service:** 주문·모의 결제·재고 관리
  - **Cooking Service:** 조리·대기열·예상 대기 시간 관리
  - **Congestion Service:** 주문량·대기열 기반 혼잡도 분석
  - **Auth Service:** 회원 인증 및 사용자 권한 관리
- **구현 순서:** Menu·Order·Cooking의 기본 주문 흐름을 우선 통합하고 Congestion·Auth를 단계적으로 연결한다. 로그인 필수 여부에 따라 Auth 구현 우선순위는 조정할 수 있다.
- **관리자 기능:** 초기 개발 범위에서는 구현하지 않는다. 다만 영구 제외하지 않으며, 추후 고도화 시 도입 여부·구현 범위·독립 Admin Service 필요성을 검토한다.
- **팀 확인 필요:** 5개 서비스 구성과 관리자 기능의 초기 제외 방침에 대한 팀 전체 승인.
- **관련 미결정 사항:** 로그인 세부 범위와 권한은 PD-02, 통신·DB 구성과 역할 분담은 각 관련 항목에서 별도로 결정한다.
- **상태:** 위 내용은 현재 검토안이며, 팀 최종 승인 및 관련 기획·설계 문서 반영 전이다.

## PD-03

**재고 임시 확보 시점과 만료 정책 — 해결안 도출 · 팀 최종 승인 대기**

### 현재 구성안

- **임시 확보 시작:** 사용자가 장바구니에서 **결제 시도 화면으로 이동할 때** 재고 확보를 요청한다. 장바구니에 담는 것만으로는 재고를 확보하지 않는다.
- **실제 확보 시각:** Order Service가 재고를 확인하고 **임시 확보에 성공한 서버 시각**을 기준으로 유지 시간을 계산한다. 재고가 부족해 확보에 실패했다면 결제 진행을 허용하지 않고 부족 안내를 제공한다.
- **확보 유지 시간:** 확보 성공 시각부터 **최소 5분** 유지한다. 정확한 만료 시간은 5분 이상으로 설정하되, 최종 수치는 팀 확인이 필요하다.
- **시간 초과:** 설정된 임시 확보 시간이 경과했는데 결제가 확정되지 않았다면 확보한 재고를 **자동 반환**한다. 만료된 확보 건으로는 결제를 확정하지 않는다.
- **결제 성공:** 만료 전 결제가 확정되면 임시 확보 재고를 확정 차감하고 주문 처리를 진행한다.
- **정합성:** 여러 사용자가 동시에 결제 화면에 진입해도 재고를 초과 확보하지 않도록 하며, 만료 처리와 결제 확정이 경합해도 중복 차감·중복 반환이 발생하지 않도록 한다.
- **담당 서비스:** Order Service.
- **팀 확인 필요:** 정확한 확보 유지 시간(5분 이상), 결제 화면 이탈·사용자 취소 시 즉시 반환할지 여부, 확보 만료 후 다시 결제하려는 경우의 재시도 절차.
- **상태:** 본 내용은 현재 검토안이며 **팀 전체 최종 승인과 기획서·요구사항(기존 1분 정책)·아키텍처의 관련 표현 수정 전**이다. 해당 문서들이 이미 갱신됐거나 구현이 완료된 것으로 간주하지 않는다.

## PD-12

**API·ERD·시퀀스·배포 구성도 — 미작성·초안**

- API 설계 초안에는 메뉴 목록·상세 조회 두 항목만 있으며 상세 응답·실패 조건 일부가 비어 있음.
- 아키텍처의 정상 주문·취소·장애 시퀀스와 Kubernetes 배포 구성도는 삽입 예정.
- ZIP에 독립 ERD 문서는 없음. 스크럼의 ERD 작성 예정은 산출물 존재를 의미하지 않음.
- 요구사항은 API 경로를 C단계에서 정한다고 기록. API 초안의 경로를 최종 명세로 승격하지 않음.
- 전광판 조회 API를 주문 서비스 안에 둘지 별도 읽기 서비스로 둘지 미결정이며, 언급된 “기능 6분할 문서”는 ZIP에 없음.
- 스크럼은 US-01~22 작성 예정이나 제공 요구사항은 US-20까지. US-21·22를 만들지 않음.
- 확인 질문: 누락된 상세 설계·참조 자료가 있는가? 검토·승인된 명세는 무엇인가?
- 출처: 요구사항, 아키텍처 설계, API 설계 초안·데일리 스크럼.

## PD-13

**조리 시간·취소 경합·정합성 상세 — 미결정**

- FIFO·동시 조리 최대 1건·조리 전 취소 및 Cooking 최종 판단은 원문 정책안에 있음.
- 다중 메뉴 주문의 조리 시간 계산, 주문 확정과 대기열 등록의 실패 복구, 취소와 자동 조리 시작 경합·중복 방지 상세는 미결정.
- 비로그인 본인 취소 확인 문제는 인증 범위(PD-02)와 연동됨.
- 확인 질문: 상세 처리 순서와 실패·복구 규칙을 어떤 시퀀스로 검토할 것인가?
- 출처: 요구사항, 아키텍처 설계, 설계 결정 기록.

## PD-14

**저장소 주소와 팀 문서 운영 규칙 — 확인·승인 필요**

- Notion 팀 정보의 공식 저장소는 `ktcloud-cloudnative-2026/team02`, 현재 연결 저장소는 `ktcloud-cloudnative-2026/team02-5xx`.

- Notion 팀 규칙은 리뷰 없이 main에 바로 올리지 않는다고 적고, 기존 GitHub 안내는 리뷰 승인이 선택인 예시를 포함.
- 확인 질문: 공식 저장소와 결정 기록의 기준 위치·리뷰 규칙은 무엇인가? 이번 작업에서는 원문 주소와 저장소 설정을 변경하지 않음.
- 출처: 팀 정보, [기존 공통 규칙](conventions.md), [GitHub 가이드](github-guide.md).

## PD-15

**배포·관측 상세와 기존 템플릿 — 미결정·검토 필요**

- 기존 배포 README에는 환경 IP, kubeadm·Calico·MetalLB·local-path·Envoy Gateway·Argo CD와 폴더 안내가 있음. 이번 변경에서 보존함.
- Notion 배포 구성도는 미작성이고 요구사항은 배포·관측 도구 최종 선택을 미정으로 기록. 기존 안내를 새로운 승인으로 해석하지 않음.
- 운영(prod) 자동 배포 또는 승인 후 배포, 중앙 로그 제품·로그 필드·관측 임계값은 확인 필요.
- 기존 관측 템플릿은 request_id, Notion SR-03은 traceId·orderId를 언급. 같은 필드로 가정하지 않음.
- 확인 질문: 배포 구성·도구·운영 승인 방식·로그 규칙을 무엇으로 정할 것인가?
- 출처: 기획서, 요구사항, 아키텍처 설계, 설계 결정 기록, [배포 README](../deploy/README.md), [관측 설계](observability.md).

## PD-16

**원문 표현과 예시 정리 — 확인 필요**

- 기획서 10장의 문장 앞에 “주문 앱의 점주용 관리 화면우리 팀은”이 붙어 있음. 임의 교정하지 않고 보존함.
- 원문 작성 안내·예시·빈 체크리스트를 프로젝트 기능·승인·완료 증거와 구분함.
- 회의록·스프린트·학습 노트는 빈칸·예시 중심이며 스크럼에는 실제 일부 기록이 있음. 모두 완료된 회의 실적으로 간주하지 않음.
- 확인 질문: 원문의 문장 정리와 양식·실제 기록 분리는 후속 단계에서 어떻게 진행할 것인가?

## PD-17

**비밀번호 저장 표현과 정책 — 팀 확인·승인 필요**

- Notion 요구사항 US-14는 “비밀번호는 암호화로 저장”, 기획서 7장 개인정보·윤리·저작권 항목은 “비밀번호는 해시로 저장”으로 표현합니다. 두 원문 표현을 보존하고 차이를 기록합니다.
- **검토 방향(원문 외 보충):** 암호화와 해시는 다른 방식입니다. 향후 비밀번호 저장 정책은 안전한 단방향 해시 방식으로 검토할 사항입니다. 특정 제품·알고리즘·인증 방식을 확정하지 않습니다.
- 확인 질문: 비밀번호 저장 정책과 용어를 어떤 팀 합의에 따라 정리할 것인가? US-14 자체의 승인과 구분해 검토해야 합니다.
